# Benchmark evidence and optimisation v1

This implements roadmap #9's P0 issues #4, #3 and #5. It extends the existing FIFO worker, native Vulkan runtime and append-only artifacts. Qualification definitions, deterministic grades, performance workloads, long-context generator and `benchmarks/versions.lock.json` remain unchanged. Changes to the measured harness produce a different comparison hash; do not mix old and new harness groups as equivalent measurements.

## Additive evidence format and backward reads

New manifests and sample `diagnostics` declare `benchmark-evidence-v1`. This is additive derived metadata, not a new scoring version. Raw `response`, `events`, native `usage`, `native_timings`, requests and original grades remain evidence. API reads of older artifacts derive diagnostics from saved counters and timing fields without rewriting files or checksums. Missing historical counters remain unavailable. Timestamp-derived durations are labelled; absent phase durations are not invented. Regraded runs use the source inference duration, rather than the time spent regrading. Interrupted runs have only the last persisted timing snapshot, a lower bound before interruption.

Capability samples store wall-clock sample duration (template/tokenizer preparation, request and grading), request duration, native prompt and generation duration, and their sum as inference duration when both native durations exist. TTFT measures first streamed content/reasoning/tool delta. TTFA measures first answer/tool delta; it is unavailable in diagnostics for embedded `<think>` content because its first content delta can still be reasoning. Original historical timing fields are retained. Neither metric claims token-precise transport timing.

Prompt and generated tokens come from native usage, falling back to native timing counters. Zero is retained as a measured zero. Capability requests also count the rendered chat template with the backend tokenizer before inference, providing a fallback prompt count if a stream dies. If template/tokenizer support is absent or the backend dies before supplying usage, the affected count stays unavailable. Reasoning and final-answer token counts require explicit native `completion_tokens_details.reasoning_tokens` / `final_answer_tokens`. No subtraction, text tokenisation or SSE chunk count estimates a split. Many llama.cpp builds do not expose these splits.

Failed/cancelled streams retain all counters, stop state and timings received so far, plus partial text and events. A native `length` finish is marked token-budget truncation. Unknown finish state remains null, rather than being declared untruncated.

Diagnostics classify failures without changing the grade: `wrong_answer`, `extraction_mismatch`, `schema_failure`, `malformed_structured_output`, `malformed_tool_call`, `tool_selection_failure`, `token_budget_truncation`, `timeout`, `inference_error`, `parser_or_harness_error`, `unavailable_grade`, and `cancelled`. The frozen grader's detail and unit cases remain available. A syntactically valid JSON value with the wrong schema differs from invalid JSON and from a wrong value that satisfies the schema. Unavailable final-answer extraction keeps the existing unavailable grade.

## Duration and efficiency

Job submission, worker start and run finish timestamps remain in evidence. Monotonic clocks record queue wait, active run duration and total elapsed (queue plus active). Active duration includes verification/setup, model loads/warmup, performance, capability, grading/aggregation, cleanup and other harness work. Phase buckets are exclusive and sum to active duration; repeated phase invocations accumulate. Final archive hashing and job bookkeeping follow the measured run and are not model execution time. Queue wait never enters efficiency denominators.

Token totals cover recorded capability/performance samples, or tuning performance/guardrail samples for optimisation. Warmup and chat health observations are separate artifacts, excluded from these totals. Totals include failed and truncated responses when native counters exist, and each total reports observed sample coverage. An incomplete total is an observed subtotal, never a claimed full total.

Capability response-length and sample-duration distributions report count, median and nearest-rank p95 (`ceil(.95 * n)`, one-based), including failed responses with available evidence. Samples/minute counts executed measurement samples; scheduled-but-unexecuted failure placeholders stay in reliability/coverage but do not count as completed work. Correct capability samples/minute counts only valid deterministic full passes, using the entire active run as denominator. Output tokens/correct answer divides all capability output tokens, including incorrect/truncated attempts, by valid full passes. The ratio is unavailable without complete capability output-count coverage or any correct answer. Output tokens/minute is unavailable without complete measured-sample output-count coverage.

Cancelled, failed, interrupted and partial runs retain diagnostic totals/distributions, elapsed timing and phase evidence. They are visibly partial and ineligible for completed qualifications. Leaderboard uses completed nonsmoke benchmark runs only. Compare can display diagnostic runs with an explicit warning and `comparable: false`; it can sort by active duration or correct capability samples/minute. These metrics supplement capability and reliability, never replace them.

## Optimisation objectives

`optimisation_objective` and `profile_name` are separate request/manifest fields. The name is any validated profile name. For old API clients that omit the objective, a name of FAST/BALANCED/SMART retains its former intent; other names default to BALANCED. Historical optimisation manifests remain readable, with their original results and objective semantics preserved.

The new optimiser declares `capability-guarded-tuning-v1` and snapshots the distinct `unscored-tuning-v1` definitions/source. It refuses exact scored prompt or ID reuse before launching candidates. Qualification prompts, scoring rules and results are never inputs to tuning. Guardrail samples use a separate `tuning_guardrail` record type and never enter qualification capability scores.

- **FAST:** repeated fixed-length runtime workloads plus templated chat health, maximising native decode tokens/second. No capability guardrail.
- **BALANCED:** the same runtime stability checks plus two small instruction/structured-extraction tasks, each repeated with the requested repeat count. Maximise fixed-workload speed (`1 / (256 / prompt_tps + 128 / generation_tps)`) while retaining every baseline guardrail task/repeat pass. Faster candidates that lose even one baseline pass are rejected. An unavailable baseline guardrail prevents guarded selection.
- **SMART:** four tasks including arithmetic and ordering reasoning. Retain baseline passes, then prefer guardrail pass rate, tested stable context, and fixed-workload speed in that order. Without an explicit context sweep, an early bounded candidate toggles the generic thinking switch and increases the configured budget; effective generation remains bounded by context. Explicit context sweeps spend the candidate budget on those contexts. Template-specific support and reasoning benefits must be measured; a requested switch does not prove support.

The exact selected profile is always the first baseline, including with context sweeps. Budgets remain caps and repeats remain at least three. A zero-pass baseline can still yield a runtime winner if no pass regresses; the report exposes the zero, and no semantic capability improvement is claimed. Small public guardrails are neither comprehensive nor contamination resistant. SMART remains tuning intent rather than a measured intelligence label.

`optimisation-report.json` and the Run page show baseline/candidate/winner configs, rejected/failed candidates, objective components, runtime-score improvement against baseline, contexts/repeats, setting deltas and whether sampling/reasoning settings changed. Partial reports survive cancellation; a proposed best candidate in a partial report is not a saved winner. Failed baseline performance leaves runtime gain unavailable. Thread/batch/ubatch/offload tune runtime execution. Context and cache precision can affect answer behaviour. Sampling/template/reasoning settings can alter responses. No runtime tuning changes the model's base intelligence, and each winner still needs separate scored qualification.
